# ADR 0001 — Knowledge Graph 2.0: Postgres + pgvector + Apache AGE / recursive CTEs

- **Status:** Proposed (future 2.0 release)
- **Date:** 2026-10-04
- **Deciders:** Chris Castro
- **Epic:** RCL-44 (KG 2.0) — see Jira RCL board
- **Supersedes storage choice in:** RCL-30 (KG Sprint 1, Qdrant-backed)
- **Context tickets:** RCL-30 (design), RCL-39 (prod rollout), RCL-43 (traverse latency)

## 1. Context

Sprint 1 (RCL-30) shipped the Memory Twin knowledge graph on **Qdrant**, reusing the
vector store that memory-twin already ran. That was the correct call to ship: zero new
infrastructure, one backup story, one operational surface, and the KG's semantic
operations (`kg_resolve`, duplicate detection, memory↔graph bridge) are genuinely
vector-similarity workloads that Qdrant does well.

The RCL-43 latency investigation exposed the structural limitation of that choice.
Depth-3 `kg_traverse` measured **p95 ~400ms in-cluster** against the §10 SLO of
<150ms. Profiling established the cause is **not** the Python code (~1.5ms in-process),
**not** storage (Qdrant payload reads ~4ms even on networked iSCSI), and **not** CPU
saturation. It is **architectural**: Qdrant has no native graph traversal, so every hop
is orchestrated from the application as separate round-trips:

```
per hop (direction=both): edges_from (src match) + edges_to (dst match) + get_entities
```

RCL-43 combined the two directional edge queries into one (3→2 round-trips/hop), cutting
in-cluster depth-3 p95 from ~400ms to ~217ms (~45%) — a real win, but still over SLO,
because the traversal cost is inherently **O(depth) network round-trips** when you
simulate a graph over a document store. No amount of client tuning makes that O(1).

The KG is also a **hybrid semantic-graph**: it needs both vector similarity (resolve,
dedup) and graph traversal (traverse, path, impact). Few single engines do both well.

This ADR proposes the long-term 2.0 storage architecture. **It is not a near-term
migration** — the prod graph is ~22MB and dozens of entities today; Qdrant is fine at
this scale. This records the target so the decision is deliberate when scale justifies it.

## 2. Current state (what 2.0 must preserve)

### Data model (src/memory_mcp/kg/models.py)

| Type | Fields | Vectorized? |
|---|---|---|
| **Entity** | key, provider, type, kind, native_id, display_name, aliases[], properties{}, memory_ids[], agent, created_at, updated_at, valid_from, valid_to | **Yes** — 384-dim MiniLM over `display_name + aliases + type` |
| **Edge** | src, relation, dst, properties{}, evidence_memory_ids[], agent, created_at, valid_from, valid_to, retire_reason | No |
| **XRef** | src (fq), relation, dst (fq), note, evidence_memory_ids[], agent, created_at, valid_to, dangling | No |

- **Multi-graph:** independent graphs (`vtv`, `mcit`, …), physically separate Qdrant
  collections `kg_<graph>_entities` / `kg_<graph>_edges`, plus a shared `kg_xrefs`.
- **Temporal:** soft-retire via `valid_from` / `valid_to`; `as_of` time-travel queries.
- **Relations:** registry-defined, class `topology` (intra-graph edges) or `reference`
  (cross-graph xrefs).

### Query surface (src/memory_mcp/kg/query.py — the contract to preserve)

`resolve` (vector + exact), `get_entity` (+ history), `find`, `traverse` (BFS, direction,
kinds, relations, `as_of`, depth≤6), `path` (shortest path, depth≤6), `impact`
(blast-radius BFS), `overview`, `related_across` (xref), `for_memory`, plus `import` /
`export`. Writes: `upsert_entity`, `link`, `unlink`, `retire_entity`, `batch`, `xref`.
16 `kg_*` MCP tools + REST under `/kg`. **Any 2.0 store must keep this surface and the
§10 acceptance checks green** — the swap is storage-layer only, behind the existing
`GraphStore`/`KGQuery` seam.

## 3. Decision

Adopt **PostgreSQL as the single system of record for KG 2.0**, with:

- **pgvector** for the semantic layer (entity embeddings; `resolve`, dedup).
- **Apache AGE** (openCypher on Postgres) *or* **native recursive CTEs** for graph
  traversal — evaluated head-to-head in the spike (RCL-45) before committing to one.
- **ACID** multi-statement transactions for write consistency (entity + edges + xref in
  one tx), replacing app-side consistency logic.
- One engine, one backup/restore story, one HA story.

### Why Postgres over the alternatives

| Option | Verdict |
|---|---|
| **Stay on Qdrant** | Fine while the graph is small/shallow. Rejected as the 2.0 target: traversal is O(depth) round-trips by construction; the SLO miss is structural, not tunable. |
| **Dedicated graph DB (Neo4j / Memgraph) + keep Qdrant** | Best raw traversal, but means running **two** stateful systems and syncing them, weak/younger vector story, and real added ops for a small team. Overkill at current scale. |
| **Embedded (KùzuDB)** | Great graph engine, embedded (no server), Cypher — but young, and still needs Qdrant for vectors. Keep as a dark-horse for the spike. |
| **Postgres + pgvector + AGE / recursive CTEs** | **Chosen.** One ACID engine does **both** vectors and graph. Recursive CTE / AGE does multi-hop traversal **in one round-trip** — directly fixes the RCL-43 problem. Mature ops, mature backup/HA, already-understood by the team. Best fit for a *hybrid* semantic-graph at this scale. |

The decisive factor: the KG is a hybrid, and Postgres is the only option that collapses
both the round-trip problem **and** the two-systems problem simultaneously.

## 4. Target schema (concrete)

Multi-graph via a `graph` column (not separate DBs), partitioned if needed later.

```sql
CREATE EXTENSION IF NOT EXISTS vector;      -- pgvector
CREATE EXTENSION IF NOT EXISTS age;         -- Apache AGE (if chosen over CTE)

-- Entities: relational columns for exact/filter, JSONB for properties, vector for resolve
CREATE TABLE kg_entity (
  graph         text        NOT NULL,
  key           text        NOT NULL,          -- provider:native_id
  provider      text        NOT NULL,
  type          text        NOT NULL,
  kind          text        NOT NULL,
  native_id     text        NOT NULL,
  display_name  text        NOT NULL,
  aliases       text[]      NOT NULL DEFAULT '{}',
  properties    jsonb       NOT NULL DEFAULT '{}',
  memory_ids    text[]      NOT NULL DEFAULT '{}',
  agent         text        NOT NULL,
  created_at    timestamptz NOT NULL,
  updated_at    timestamptz NOT NULL,
  valid_from    timestamptz NOT NULL,
  valid_to      timestamptz,                    -- NULL = current
  embedding     vector(384),                    -- MiniLM; resolve/dedup
  PRIMARY KEY (graph, key)
);
CREATE INDEX ON kg_entity USING hnsw (embedding vector_cosine_ops);  -- semantic
CREATE INDEX ON kg_entity (graph, kind);
CREATE INDEX ON kg_entity (graph, provider, type);
CREATE INDEX ON kg_entity USING gin (aliases);
CREATE INDEX ON kg_entity USING gin (properties);

-- Edges: the adjacency; indexed both directions for traversal
CREATE TABLE kg_edge (
  graph               text        NOT NULL,
  src                 text        NOT NULL,
  relation            text        NOT NULL,
  dst                 text        NOT NULL,
  properties          jsonb       NOT NULL DEFAULT '{}',
  evidence_memory_ids text[]      NOT NULL DEFAULT '{}',
  agent               text        NOT NULL,
  created_at          timestamptz NOT NULL,
  valid_from          timestamptz NOT NULL,
  valid_to            timestamptz,
  retire_reason       text,
  PRIMARY KEY (graph, src, relation, dst, valid_from)
);
CREATE INDEX ON kg_edge (graph, src) WHERE valid_to IS NULL;   -- outbound, current
CREATE INDEX ON kg_edge (graph, dst) WHERE valid_to IS NULL;   -- inbound, current
CREATE INDEX ON kg_edge (graph, src, valid_from, valid_to);    -- as_of
CREATE INDEX ON kg_edge (graph, dst, valid_from, valid_to);

CREATE TABLE kg_xref (
  src                 text        NOT NULL,     -- fully qualified graph::key
  relation            text        NOT NULL,
  dst                 text        NOT NULL,
  note                text        NOT NULL,
  evidence_memory_ids text[]      NOT NULL DEFAULT '{}',
  agent               text        NOT NULL,
  created_at          timestamptz NOT NULL,
  valid_to            timestamptz,
  PRIMARY KEY (src, relation, dst)
);
CREATE INDEX ON kg_xref (src);
CREATE INDEX ON kg_xref (dst);
```

### Traversal in ONE round-trip (the RCL-43 fix)

Recursive CTE replaces the Python BFS + N round-trips with a single server-side query.
`traverse(start, direction=both, max_depth=3, as_of=t)` becomes:

```sql
WITH RECURSIVE reach AS (
  SELECT :start AS key, 0 AS depth
  UNION
  SELECT CASE WHEN e.src = r.key THEN e.dst ELSE e.src END, r.depth + 1
  FROM reach r
  JOIN kg_edge e
    ON e.graph = :graph
   AND (e.src = r.key OR e.dst = r.key)              -- direction=both
   AND e.valid_from <= :as_of
   AND (e.valid_to IS NULL OR e.valid_to > :as_of)   -- temporal / as_of
  WHERE r.depth < :max_depth
)
SELECT DISTINCT key, min(depth) FROM reach GROUP BY key;
```

`as_of` is a WHERE predicate (no second code path). `path` → recursive CTE carrying the
path array + cycle guard. `impact` → directed variant. `kinds`/`relations` filters →
extra JOIN predicates. All **one query, in-engine**, eliminating the O(depth) round-trips.

Apache AGE alternative: the same expressed as openCypher
(`MATCH (a)-[*1..3]-(b) WHERE ...`), evaluated in the spike for ergonomics vs raw CTE.

### Semantic layer (unchanged behavior)

`resolve` = pgvector KNN (`ORDER BY embedding <=> :q LIMIT k`) UNION exact matches on
`aliases`/`native_id`/`display_name` — same two-pass logic as today, one SQL statement.

## 5. Migration strategy (phased, reversible)

1. **Spike (RCL-45):** stand up Postgres+pgvector+AGE; prototype `traverse`/`path`/
   `impact` as CTE **and** AGE; benchmark depth-3/6 vs the Qdrant baseline on the mcit
   acceptance seed. Decide CTE vs AGE. Exit criterion: depth-3 p95 < 150ms in-cluster.
2. **Schema + migrations (RCL-46):** the DDL above, Alembic/SQL migrations, in infra-tf.
3. **Store adapter (RCL-47):** implement a `PostgresGraphStore` behind the existing
   `GraphStore` interface; feature-flag `KG_BACKEND=qdrant|postgres`. No change to
   `KGQuery`/tools/REST surface.
4. **Query rewrite (RCL-48):** move traverse/path/impact into SQL (the win); keep
   `KGQuery` as a thin orchestrator.
5. **Data migration + backfill (RCL-49):** export from Qdrant (existing `/kg/export`),
   load into Postgres, re-embed entities; dual-write window for safety.
6. **Acceptance parity (RCL-50):** §10 checks green on Postgres; parity diff vs Qdrant.
7. **Cutover + rollback (RCL-51):** flip `KG_BACKEND` per environment (dev → prod);
   rollback = flip back (Qdrant collections retained through the window).
8. **Ops (RCL-52):** Postgres HA, backup/restore runbook, monitoring, CSI storage on
   mcit-k8s. Decommission the KG Qdrant collections once stable.

## 6. Consequences

**Positive**
- Traversal becomes O(1) round-trips → fixes the RCL-43 SLO structurally.
- One ACID engine for graph + vectors; multi-edge writes become real transactions.
- Mature backup/HA/monitoring; team already knows Postgres.
- Richer queries (shortest-path, pattern, weighting) become tractable.

**Negative / risks**
- pgvector HNSW at very large scale is less specialized than Qdrant — acceptable at KG
  scale; re-evaluate if the KG grows to millions of entities.
- Apache AGE is less mainstream than core Postgres; the recursive-CTE path is the safe
  fallback and avoids the AGE dependency entirely.
- Migration touches the stateful system of record — must be dual-write + reversible.
- Memory-twin's *semantic memory* (the `memories` collection) stays on Qdrant; 2.0 is
  scoped to the **KG** only, so the service runs both stores during/after transition
  unless a separate decision moves memory too.

## 7. Scope boundary

2.0 covers the **knowledge graph** storage only. The core semantic-memory feature
(`save/search/list/delete_memory` over the `memories` collection) is out of scope and
stays on Qdrant unless a future ADR revisits it.
